## 发现的问题

P1 表示影响已保存比较、冻结协议一致性或模型身份，需要在宣称可复现之前修复。P2 表示可复现的程序缺陷或环境缺项，当前批次的影响另行说明。优先级不代表已证明全部现有结果无效。

### R01 · P1 · checkpoint 的登记版本没有传给模型加载

位置：`scripts/extract_representations.py:76–81`。

程序把环境变量或本地 snapshot 目录名登记成 `revision`，随后加载 tokenizer 和模型时只传模型 ID。实际加载依赖 Hugging Face 当时解析的默认版本，登记的 hash 没有约束实际权重。假加载器收到的参数中没有 `revision`，已复现。

影响：当前文件记录的 revision 尚不能单独证明所用权重身份；本次没有证据证明历史权重确实错了。后续必须显式加载已冻结 revision，并在运行记录中核验实际 snapshot。历史计算需从真实模型缓存和运行记录补查权重身份，禁止通过补写字段假定一致。

### R02 · P1 · GPU 前向精度与冻结配置不一致，缓存身份未区分精度

位置：`scripts/extract_representations.py:82–84,111–118`；`configs/probes.yaml:28–31`。

协议指定前向 fp32、存储 fp16。GPU 分支执行 `model.half().cuda()`，实际使用 fp16 模型。缓存键和 meta 未登记前向 dtype。同一序列的 CPU 与模拟 CUDA 请求命中同一缓存，已复现。

影响：`run_p402_extract_knots.sh`、`run_p405_embed.sh` 和 P5.07 提取入口使用 CUDA，相关产物需要核对历史实际精度。精度差异对现有指标的数值影响尚未测量。修订应明确实际前向精度并纳入缓存身份，分开保存新旧缓存；随后用代表性样本检查差异，再确定需要重提取及重算的范围。已有缓存的 meta 没有前向 dtype，不能根据其存储 fp16 推断前向精度。

### R03 · P1 · 元数据基线与 PLM 的同名排名指标方向相反

位置：`scripts/metrics.py:110–113`；`scripts/run_baselines.py:123–125`；`scripts/run_probes_p303.py:339–345`；`scripts/run_l2_stage_b.py:130`。

基线使用 `mean(1-(rank-1)/N)`，越大越靠前；PLM 使用 `mean(rank/N)`，越小越靠前。两个结果都叫 `positive_rank_percentile`。四个对象中第一名的两个输出分别为 1 和 0.25，已复现。基线和 stage-B 当前宇宙均为 342,014，问题来自定义差异。

影响：现有结果表中的排名百分位不能按同一方向直接比较。recall@k 不受此公式差异影响。无需模型重跑即可统一已保存点估计；若采用 PLM 当前的 `mean(rank/N)`，换算公式为 `1-old+1/N`：

| 基线 | 当前文件值 | 换算后的 mean(rank/N)，越小越好 |
|---|---:|---:|
| B0_random | 0.4399524581 | 0.5600504658 |
| B1_length_desc | 0.5787973592 | 0.4212055647 |
| B2_n_pdb_desc | 0.3531352518 | 0.6468676721 |
| B3_logistic_len_pdb | 0.6129228628 | 0.3870800611 |

这里只提供审计换算，原结果未改写。正式修订需统一指标名称与方向，并更新使用该指标的表和文字。当前 PLM stage-B 保存值为 0.000027，仍须按既有直推、开发性诊断解释；这次换算不会产生独立泛化证据。

### R04 · P1 · P5.07 结构确认只用单向 TM-score，并容许缺失确认文件继续生成结果

位置：`scripts/p507_isolate_cluster.py:183–219`；`scripts/sbatch_p507_newnew.sh:40–59`；`scripts/p507_build_final_universe.py:81–112`。协议见 `configs/p507_type_probe_design.yaml:23`。

解析器仅取 Structure_1 归一化分数，日志写“min TM≥0.6”。输入两个方向的 0.82 和 0.40 时，程序采用 0.82，协议要求的最小值为 0.40。把输出改成 Chain_1/Chain_2 措辞后，程序返回空值。程序也未检查 US-align 返回码；带空分数的已写入配对会被加入完成集合，后续运行不重试。下游对缺失结构边文件打印警告后继续；临时 fixture 在两份确认文件都缺失时仍生成新节点结果。

当前本地表实际有 3,010 个新—旧配对及 7,962 个新—新配对，均有单向数值，没有空白分数行。缺失确认文件的分支本次未在当前真实输入中触发。两个表均只有一个分数列，其中新—新表头明确写 `tm_norm_by_q`，无法从表恢复双向最小值。

影响限定于这些 P5.07 补充处理入口。本次未发现主打结划分的既有双向 min 检查存在同一错误。单向阈值可能纳入额外绑定边；实际差集需要两向原始输出或重新确认才能量化，不能推定原分量保持不变。

修订：同时保存两个方向、实际最小值与进程状态；解析失败进入重试清单，确认完整性不满足时停止构建。核验这 10,972 个已筛选配对后重建 P5.07 分量，比较样本去留和分量变化；仅在变化影响探针输入时重算该补充探针及统计。这个修订不会自动恢复其独立验证资格。

### R05 · P2 · 统一 AP 模块未按协议处理并列分数

位置：`scripts/metrics.py:28–35`；`configs/evaluation_protocol.yaml:26–28`。

两条样本得分都是 0.5、标签为 `[1,0]` 时，本模块返回 1.0，sklearn 返回 0.5。交换标签顺序，本模块变成 0.5；协议要求并列组池化，输出不应随输入顺序变化。

影响：模块自身和调用它的残基 AP helper 有问题。当前 P3.03 主探针、P5.08 以及修订统计走 sklearn 或另一个已检查的并列组实现，本次没有发现其调用这个错误 AP 函数。因此没有依据要求所有现有 AUPRC 重算。修订该模块并添加并列输入回归例，再检查调用链。

### R06 · P2 · 缺少 FS 的 B 端时，所有配对都可静默复用 A 端

### R07 · P2 · 默认提取命令声明全部层，输出却没有表示数组

### R08 · P2 · 缓存失配重提取后清单重复记录同一个样本

位置：`scripts/extract_representations.py:126–136,165–166,176–195`。

缓存 meta 失配时先追加 `reject` 行，重提取后又追加同一个 key 的 `miss` 行，并覆盖原文件。fixture 的单样本清单变成两行。这会让打包矩阵的样本数、拒绝状态和下游记录数失真。

本次未量化历史清单中是否触发该分支。修订应将拒绝记录放到审计日志，每个请求样本仅写一个终态清单行；覆盖前保留失配文件的哈希及原因，并用临时文件完成原子写入。提取完成应检查名字/记录覆盖与请求一致。

### R09 · P2 · 管道可掩盖探针非零退出

位置：`scripts/run_p303_pipeline_rest.sh:3,11,15`。

只有 `set -e`，没有 `pipefail`。Python 若打印匹配日志后退出 7，右侧 grep 返回 0，整条管道返回 0，后续继续；小例子已复现。修订所有承担运行状态判断的管道，保留原始日志并检查计算进程退出码。本次没有证明历史任务曾因此错误续跑。

### R10 · P2 · 公布的环境锁不含 scikit-learn，多个执行入口依赖固定绝对路径

修订应区分历史作业脚本与正式复现入口，提供可配置项目根目录和集群工具位置；以实际使用环境补齐依赖及来源，做干净环境的小规模复跑。只做语法检查不足以验收这项。
